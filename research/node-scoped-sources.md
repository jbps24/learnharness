# Research: scoping source material to a plan node

Wayfinder ticket: "Research: scoping source material to a node".

Question: the app is moving toward teaching each plan node (a node of the mermaid DAG written by
`plan_init`) in its own small model context. How could that node context get only the source
material it needs, for example one chapter of a course script PDF that runs to hundreds of pages?

Scope: read-only investigation of this repository at commit `37ec55e`, plus one example session
record. This note reports facts and options. It does not choose a design.

All paths are relative to the repo root. `file:N` means line N, and `file:N-M` means a range.

---

## 0. The current PDF path, end to end

1. **Teacher-facing tool `pdf`.** The input is `{ path, question }` and nothing else
   (`src/agent/tools/jobs.ts:70-77`, contract `PdfToolInput` at `src/core/contracts/jobs.ts:263-268`).
   The tool is fire-and-forget. It resolves the path against the file-access policy, creates a job and
   returns an acknowledgement (`src/agent/tools/jobs.ts:173-183`, ack text at `:105-107`, description at
   `:127-132`). It is available to the teacher, the prober (`src/agent/tools.ts:336-337`) and practice
   (`src/agent/tools/practice.ts:216`). The teacher prompt tells it to give the path and "the specific
   question you need answered" (`src/agent/prompts/teacher/40-jobs.md:16`).
2. **Job runner.** `runPdfJob` (`src/agent/subagents/runner.ts:495-529`) calls `runPdfReaderAgent({ path, question })`.
   The reader's token usage is folded into the turn's usage steps through `loop.onUsage`
   (`runner.ts:517`), so the record has no separate per-job cost.
3. **Reader sub-agent.** `src/agent/subagents/pdf-reader.ts` runs a hand-rolled loop with four tools:
   `pdf_info`, `pdf_extract(pages)`, `pdf_render(pages, dpi)` and `pdf_search(query, context_lines, literal)`
   (`pdf-reader.ts:88-125`). Its first prompt carries only the path and the question (`:199-204`). Its
   final assistant text is the brief (`:237-255`).
4. **Library layer.** `src/agent/subagents/pdf-ops.ts` holds `pdfInfo`, `pdfExtract`, `pdfSearch`,
   `parsePageSpec` and `convertPdf`, all built on pdfjs-dist. Text comes out as Markdown generated by rule,
   with no model involved, in `src/agent/subagents/pdf-markdown.ts` (`documentToMarkdown` at `:264-291`,
   `joinPages` at `:294-296`).
5. **Delivery.** `buildSubagentSteer` (`src/core/contracts/jobs.ts:407-425`) builds a `role: "custom"`,
   `customType: "subagent-steer"` message.
   - `content` is `steerText(...)`. For a successful PDF read that is the prefix
     `PDF reading complete — the reader's brief on "<path>" follows, with page citations. Weave it into
     the lesson and cite pages when you use it:` followed by the brief (`jobs.ts:387-388`).
   - `details.result` carries the full `PdfResult` (`path`, `question`, `brief`, `pagesRead`,
     `pagesConsulted`, contract at `jobs.ts:270-284`). Only `content` reaches the model; `details` is
     UI-only (`jobs.ts:290-293`).
6. **Researcher variant (web PDFs).** `src/agent/tools/pdf-read.ts` gives the researcher sub-agent
   `web_fetch_pdf`, `pdf_info`, `pdf_extract` and `pdf_search`. These are scoped to a per-job temp dir
   (`pdf-read.ts:43-50`, `:79-213`). The runner creates the dir with `mkdtemp` and deletes it after the
   job (`runner.ts:372`, `:405`). This path has no `pdf_render` (`pdf-read.ts:17-20`). It is not the path
   used for a learner's local PDF.

## 1. Can the reader read by chapter or page range today? What parameters exist?

**At the `pdf` tool boundary: no.** The tool exposes only `path` and `question`
(`src/agent/tools/jobs.ts:70-77`). It has no `pages`, `section` or `chapter` field. Any scoping is free
text inside `question`.

**Inside the reader: yes, by page range, chosen by the reader model.**

| Tool (reader loop) | Parameters | Limits |
|---|---|---|
| `pdf_info` | none | Walks every page and returns `text_length`, `image_count` and `math_density` per page (`pdf-ops.ts:145-174`). It returns no outline or table of contents. |
| `pdf_extract` | `pages`: `'all' \| '1-5' \| '1,3,7' \| '3'` (`pdf-reader.ts:95-101`) | Output is capped at 24,000 chars per call, with a notice telling the model to narrow the page spec (`pdf-reader.ts:66`, `:141-148`). Spec parsing is in `pdf-ops.ts:177-195`. |
| `pdf_render` | `pages`, `dpi` (72–300, default 150) (`pdf-reader.ts:102-112`) | At most 6 pages per call (`:64`, `:299`). |
| `pdf_search` | `query`, `context_lines` (0–8, default 3), `literal` (`:113-123`) | Returns at most 40 hits (`:289-294`). |
| Loop | none | At most 14 iterations (`:61`). |

The researcher's variant also takes page specs. Its `pdf_extract` has no 24k cap (`pdf-read.ts:179-195`),
and its `pdf_search` is literal-only (`:206`).

**Page numbering.** Page specs are 1-based physical PDF page indices, clamped to `doc.numPages`
(`pdf-ops.ts:177-195`). Nothing maps printed page labels to PDF pages. In the example session the
reader noticed by itself that "PDF-Seite = Skriptseite + 1" (PDF page = printed script page + 1) and
said so in every brief (see §3).

**Chapter or outline awareness.** No code reads the PDF outline (bookmarks). A search for
`getOutline` / `outline` in `src` finds nothing PDF-related. Headings come only from font-size
heuristics in `pdf-markdown.ts`, which emits `#`/`##`/`###` (`toBlocks` at `:216-242`) and resets per
page (`:282-287`). The reader can locate a chapter only by `pdf_search` on its title or by extracting
the table-of-contents pages.

## 2. Is a converted document (Markdown) cached and reused, or re-converted each time? Where is it stored?

**It is re-converted on every tool call. Nothing is cached or persisted.**

- `pdfExtract` opens the file and converts the requested pages on each call (`pdf-ops.ts:254-260`).
- `pdfSearch` opens the file and converts all pages on each call (`pdf-ops.ts:278`, `:291`). On a
  122-page script, every search is a full-document conversion.
- `pdfInfo` re-walks every page, including the operator list for image counts, on each call
  (`pdf-ops.ts:145-174`).
- `openDocument` reads the file from disk each time (`pdf-ops.ts:58-60`). There is no module-level map
  or cache. Searching for cache identifiers (`pdfCache`, `markdownCache`, `Map<string, PdfPage`) finds
  nothing.
- Each `pdf` job starts with an empty context: path and question only (`pdf-reader.ts:199-206`). It
  re-triages the document. In the example session, five `pdf` jobs read the same 122-page PDF, and each
  started from `pdf_info` per its doctrine (`pdf-reader.ts:37-39`).
- `renderDir()` (`pdf-ops.ts:314-324`, a `/tmp/lh-pdf-<hash>` path) is exported but has no caller in
  `src`. It is dead code, not a cache.

**The other places that convert a PDF don't persist the Markdown either:**

- **Graph notes import.** `POST /api/graph/import` calls `convertPdf(bytes, 1000)` and then
  `joinPages(...)`, which produces `--- Page N ---`-marked Markdown (`app/api/graph/import/route.ts:55`,
  `:61-82`). It passes the text straight into `extraction.importNotes`
  (`route.ts:126`, `src/agent/subagents/extraction.ts:1411-1425`).
  - The stored `NotesSource` holds only `id`, `filePath`, `importedAt` and usage
    (`src/core/contracts/graph.ts:80-92`).
  - The Markdown is split in memory into chunks of about 4096 tokens (`extraction.ts:1245-1260`, default
    `src/core/settings.ts:555`) and then discarded.
- **Plugin `documents.toMarkdown`.** It is in-memory "without saving it"
  (`docs/plugin-api/plugins.md:978-996`, `src/server/plugin-documents.ts:16-77`). The output is capped at
  2 MiB (`plugin-documents.ts:8`, `:71-73`), with at most 1000 pages (`:9`).

**Storage locations that do exist:** the original PDF stays wherever the learner keeps it, behind the
file-access policy (`resolveSourcePath`, `src/agent/tools/fs-shared.ts:182`). Researcher downloads go to
a temp dir that is deleted after the job (`runner.ts:372`, `:405`).

## 3. What does a returned brief cost?

### Limits in code

No code caps the brief's length. The only steer is the format instruction: "2-6 sentences (or short
sections) … each claim cited as (p. N). End with a line 'Pages consulted: …'" (`pdf-reader.ts:56-59`).

The inputs that feed the brief are bounded:

- 24k chars per extract (`:66`)
- 40 search hits (`:289`)
- 6 rendered pages per call (`:64`)
- 14 iterations (`:61`)

The steer adds a fixed prefix of about 220 chars to the brief (`jobs.ts:388`).

The repo's own token heuristic is chars / 4 (`src/core/compaction.ts:127`, also
`extraction.ts:1251`). The token figures below use that heuristic. They are estimates, not
tokenizer counts. German and math-heavy text probably tokenizes denser than that.

### Example session `chat_mwm3m4gq_da9d7aba.json`

Only the `subagent-steer` messages whose content starts with "PDF reading complete" were read. All five
target the same file, `…/Regelungssysteme/Regelungssysteme_WS2425.pdf`, a 122-page course script.

| msg # | Question (abridged) | content chars / bytes | brief words | ≈ tokens (chars/4) | pagesRead | pagesConsulted | `details` JSON bytes |
|---|---|---|---|---|---|---|---|
| 10 | Full outline: chapters and subchapters with page numbers | 7,563 / 7,868 | 1,063 | ~1,900 | 74 | 77 | 9,662 |
| 74 | Ch. 4.1 (pp. 39–40), Ch. 5.2 (pp. 53–55), 3.2.2 (p. 33) | 3,965 / 4,213 | 634 | ~990 | 15 | 32 | 5,782 |
| 91 | Ch. 1.2 (pp. 7–9), 4.1 & 5.1 (pp. 39, 49–52), 5.2.3 (p. 55) | 4,660 / 4,935 | 723 | ~1,170 | 16 | 29 | 6,458 |
| 97 | Ch. 2 PID (pp. 13–24, excluding 2.3) | 4,248 / 4,410 | 681 | ~1,060 | 12 | 14 | 5,593 |
| 147 | Ch. 2, sections 2.4–2.5 (printed pp. 18–24 / PDF pp. 19–25) | 5,390 / 5,579 | 817 | ~1,350 | 11 | 16 | 6,799 |

What the data shows:

- **Size.** Chapter-scoped briefs run about 4–5.4 KB, roughly 1.0–1.35k tokens, about 630–820 words.
  The outline brief is about 7.6 KB, roughly 1.9k tokens. Every brief exceeds the "2-6 sentences"
  instruction and uses structured sections instead.
- **Questions already name page ranges.** From the second call onward, the teacher put page ranges into
  the free-text `question`, using numbers it got from the first (outline) brief. The reader stayed close
  to those ranges: `pagesRead` was 11–16 pages. It still ran search hits elsewhere in the document; for
  example, msg 74 consulted pages 4, 20, 44, 101 and 119.
- **Page offset.** Every brief explains the printed-page-to-PDF-page offset of +1. Excerpt from msg 97:
  "Kapitel 2 „PID-Regler" — Skript-S. 13–24 (PDF-Seiten = Skript-Seite + 1)". Excerpt from msg 10:
  "Zitiert wird die *gedruckte* Skript-Seitenzahl; die PDF-Seite ist jeweils um +1 verschoben
  (Skript S. 7 = PDF S. 8)".
- **Planning order.** `plan_init` was called at msg 19, after the outline brief at msg 10. The saved
  tree has 16 nodes and 22 edges, each node only `{ id, title }`, for example
  `{id: "pid", title: "PID-Regler, Windup, Einstellregeln"}`. The page ranges the teacher knew at
  planning time were not stored on any node. Later `pdf` calls restated them from the transcript.
- **Reader cost.** The reader's own token spend (its triage, extracts and renders) is not separable in
  the record. It is folded into the turn usage steps (`runner.ts:517`).

## 4. Could a plan node carry a source anchor (pages or section) at planning time?

### What the contract holds today

- `PlanNode` is `{ id, title, summary? }` (`src/core/contracts/plan.ts:13-20`). `PlanTree` is
  `{ nodes, edges, version }` (`:29-34`). The tree carries structure only, by design (`:36-40`).
- `plan_init` takes one argument, `mermaid: string` (`src/agent/tools/plan.ts:52-60`). It parses with
  `parseMermaidPlan`, validates with `createTree` and persists with `chatStore.saveTree` (`plan.ts:79-90`).
- The model-facing result is `{ ok, nodeIds, reminder }`. The full tree goes in `details` only
  (`plan.ts:95-101`).
- The parser accepts `id`, `id[title]`, `id("title")`, `id(title)` and edges
  (`src/agent/tools/mermaid-plan.ts:17-28`, `ENDPOINT_RE` at `:55`). It produces `{ id, title }` only
  (`:156-159`). It skips `%%` comment lines (`:109`) and rejects subgraphs, styles and classes
  (`:146-149`). `[`/`]` cannot appear inside a title (`ENDPOINT_RE`).
- `PlanNode.summary` exists, but the mermaid parser never sets it. `createTree` copies every node field
  (`{ ...n }`, `src/core/plan-tree.ts:125`). `planTreeToText` renders `summary` when present, so it
  survives compaction (`src/core/compaction.ts:371-386`).
- The `PlanTree` / `PlanNode` types are used only in `src/core/plan-tree.ts`,
  `src/core/contracts/plan.ts` and `src/agent/tools/mermaid-plan.ts`. The plan popup reads
  `details.tree`. The `plugin-tree` module is an unrelated plugin widget (`src/core/plugin-tree.ts:1`).

### What a source anchor would need

The options below are possibilities, not recommendations.

**A. Anchor data on `PlanNode`.** Add an optional field to `PlanNode`, for example a source reference
holding a path plus a page spec and/or a section label. `createTree` already passes extra fields
through (`plan-tree.ts:125`), and `saveTree` persists the tree object (`src/store/chats.ts:222`).
Open contract questions:

- Which page numbering: the physical PDF index (what `parsePageSpec` uses, `pdf-ops.ts:177`) or the
  printed label (what the briefs cite)?
- One source per node, or several?
- Does a rewrite keep anchors, given that `plan_init` replaces the tree wholesale (`plan.ts:24-41`)?

**B. How the teacher writes the anchor.** The single `mermaid` string has no slot for it today.

| Variant | What it involves |
|---|---|
| B1. Second `plan_init` argument | For example a map `nodeId → anchor`. It is validated against the parsed ids after `parseMermaidPlan`, the same way `createTree` validates edge endpoints (`plan-tree.ts:112-117`). |
| B2. Extended mermaid subset | `%%` directive lines are already ignored (`mermaid-plan.ts:109`), or a new endpoint syntax. Either way it changes the documented grammar (`mermaid-plan.ts:13-28`) and the tool description (`plan.ts:56-58`, `:67-72`). |
| B3. Free text in `title` or `summary` | No contract change, but the anchor is not typed or machine-readable. |

**C. Where the anchor data comes from at planning time.** In the example session the teacher already
had a page-numbered outline from a `pdf` brief before calling `plan_init` (§3). The repo has no
structured outline source: no PDF-outline reading (§1), and `pdf_info` returns per-page signals only.
An anchor written at planning time would therefore be the teacher's transcription of a brief, and the
printed-versus-PDF offset would have to be reconciled somewhere.

**D. Consumers that would need to know about the anchor.**

- The `pdf` tool input (today `{path, question}`, `jobs.ts:70-77` / `contracts/jobs.ts:263-268`). It
  would need, for example, an optional page scope that the reader clamps its `pdf_extract`, `pdf_render`
  and `pdf_search` to. Today `pdf_search` always converts and scans every page (`pdf-ops.ts:291`).
- Whatever builds the node context.
- The plan popup and compaction, if the anchor should be visible (`compaction.ts:371-386` renders only
  `title`, `id` and `summary`).

## 5. Other ways a node context could reach the source

| Route | What exists today | Constraints / gaps |
|---|---|---|
| **`pdf` job per node** (status quo, scoped by `question`) | Works now. The example shows chapter-scoped questions yielding about 1–1.35k-token briefs (§3). | The result is asynchronous: a steer that arrives later (`jobs.ts:105-107`). Each job re-converts and re-triages (§2). The page scope is only advisory text. The brief is a lossy summary written by the reader, not the source. |
| **`read` on a converted Markdown file** | `read` is always on for teacher, prober and practice (`src/agent/tools.ts:326`, `:457`, `practice.ts:211`). It supports `offset`/`limit` and caps output at 2000 lines or 50 KB (`src/agent/tools/read.ts:32-33`, `:37-38`, `:46-79`). | No converted `.md` file exists anywhere (§2). `read` on the `.pdf` itself decodes raw bytes as UTF-8 (`read.ts:100-118`); it only special-cases images. A persisted Markdown would need a home inside the file-access policy (`resolveSourcePath`, `fs-shared.ts:182`). Page markers (`--- Page N ---` from `joinPages`, `pdf-markdown.ts:294-296`) would give `grep`-able anchors, but `read` slices by line, not by page. |
| **`grep` on a converted Markdown file** | It is a pure-Node scan with context lines and a 100-match default (`src/agent/tools/grep.ts:20-40`). | It skips files over 2 MB and files that look binary, judged by a NUL byte in the first 8 KiB (`grep.ts:32`, `:120-121`, `fs-shared.ts:353-362`). A raw PDF is either skipped or searched as raw bytes, never as text. A converted Markdown of a few hundred pages would likely stay under 2 MB; the plugin converter's own cap for the same conversion is 2 MiB (`plugin-documents.ts:8`). |
| **Graph import of the script** (`/api/graph/import`) | It converts a PDF of up to 1000 pages to page-marked Markdown and runs extraction → audit → merge into graph propositions (`route.ts:55-82`, `extraction.ts:1300-1408`). Graph readers exist for the prober and practice (`proberGraphTools`, `src/agent/tools.ts:340-341`, `practice.ts:217`). | The output is distilled propositions (`GraphNode` `{name, statement, aliases, provenance}`, `src/core/contracts/graph.ts:113-134`), not source text. Provenance for imports is the file (`chatId` = `src_…`) with no page or section anchor (`graph.ts:68-74`). The Markdown is discarded after chunking (§2). The teacher's tool registry (`src/agent/tools.ts:450-470`) has no graph tools. |
| **Plugin `documents.toMarkdown`** | It converts an uploaded File to Markdown in memory and returns it to a plugin frontend (`docs/plugin-api/plugins.md:978-996`). | It saves nothing and is a frontend/plugin capability, not an agent tool. The output cap is 2 MiB. |
| **Reuse the reader's building blocks directly** | `documentToMarkdown(doc, pageNumbers)` already converts any page subset, and formatting is page-local "so search and selected reads agree" (`pdf-markdown.ts:262-264`, `:282-284`). `pdfExtract(path, spec)` returns `--- Page N ---`-headed Markdown for a spec (`pdf-ops.ts:254-260`). | Nothing calls these outside the reader and researcher today. Injecting extracted pages directly, without a model, would hand a node context raw page Markdown instead of a brief. For a chapter of about 12 pages, the reader's per-call extract cap of 24k chars (about 6k tokens) gives a scale reference, but no limit applies outside the reader loop. Image-only pages yield no text (`pdf-markdown.ts:278-280`); OCR is not supported (`route.ts:76-78`). |

## Facts most relevant to a decision

The facts most relevant to whatever design is chosen, without recommending one:

- Page scoping exists only inside the reader and only as model-chosen page specs. The `pdf` tool cannot
  express it (§1).
- Nothing converted is cached or stored. Every reader tool call re-parses the PDF, and every search
  converts all pages (§2).
- Chapter-scoped briefs in the one real session are about 4–5.4 KB, roughly 1–1.35k tokens, and
  consistently exceed the "2-6 sentences" format (§3).
- The teacher had page anchors before planning, but `PlanNode` has no field for them. `summary` exists
  but is unused by the mermaid parser (§4).
- No code maps printed page labels to PDF page indices or reads PDF outlines (§1, §4C).
